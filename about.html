About

How I work

UX/product designer based in Frederick, MD. Every screen I ship answers to a specific research finding, not a hunch, and every claim in a case study traces back to a source or a test result.

Career context

I don't have a prior design internship. What I have instead is a case study built the way I'd want a junior hire's first real project to look: research traced to sources, design decisions traced to research, results traced to actual usability testing, not opinion. Convoy, a full-stack PWA I designed and built solo for a real client, is a second proof point, shipped and in daily production use, not a mockup. Reframing Letterboxd and CivicPulse round it out: a streaming-app redesign built on competitive research, and a civic-transparency concept grounded in real Baltimore data. Different problems, same rigor.

My background is in digital arts and media design (B.A., New Media, Penn State), visual systems and interaction design before UX was the explicit job title. Freelance client work built the end-to-end fundamentals: research, wireframing, hi-fi prototyping, client handoff, and iteration. I went deep on a healthcare AI case study because the problem (a person deciding whether to trust a model's output under time pressure) is a genuinely hard design problem worth solving carefully, not because I'm narrowing to healthcare as an industry. I'm looking for any UX or UX-adjacent role where that same rigor applies.

Process

Roughly the same four moves on every project, healthcare dashboard or civic-tech concept alike. I run a Stark accessibility audit before any design is considered final, WCAG 2.2 AA minimum, and I work with the tools that sit under the interface, not just around it: the Claude API directly, to prototype and debug the structured data (tool schemas, extraction logic) that AI-forward products depend on, so I catch a mislabeled field before it becomes a UI bug instead of after.

1. Ideate

Frame the problem against real sources, not a hunch. Constraints, research questions, and who's actually affected, before any pixels.

2. Concept in Stitch

AI-assisted concepting to get several directions on screen fast, then pressure-test which one actually answers the research question.

3. Build in Figma

Wireframes to hi-fi on an 8pt grid with semantic tokens and real component states, a Stark accessibility pass before anything is "final."

4. Test, then ship

Useberry + SUS/NASA-TLX against real tasks, decisions traced back to what testers actually did, then build it (Claude API included) if it's going to production.
